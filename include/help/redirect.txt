*redirect* *redirection* *redir*

#REDIRECTION#

Redirections allow you to control where a command reads its input from and
where it sends its output. A redirection applies to a specific file
descriptor; if no descriptor number is given, output redirections default
to stdout (fd 1) and input redirections default to stdin (fd 0).

==============================================================================
1. Output Redirection                          *redir-output*

  `command > file`                             *redir-out*

      Redirect stdout to {file}, creating it if it does not exist or
      truncating it if it does.

      Example:
        ```echo hello > out.txt```
        ```ls 2> errors.txt       # redirect stderr```

  `command >| file`                            *redir-out-force*

      Like `>` but overrides the {noclobber} option. If {noclobber} is set,
      `>` will refuse to overwrite an existing file; `>|` forces the
      overwrite.

  `command >> file`                            *redir-append*

      Append stdout to {file}, creating it if it does not exist.

      Example:
        ```echo line >> log.txt```

==============================================================================
2. Input Redirection                           *redir-input*

  `command < file`                             *redir-in*

      Redirect {file} to stdin.

      Example:
        ```sort < unsorted.txt```

==============================================================================
3. Read-Write Redirection                      *redir-readwrite*

  `command <> file`                            *redir-rw*

      Open {file} for both reading and writing on the specified file
      descriptor (default fd 0). The file is created if it does not exist
      but is not truncated.

      Useful with the |seek|(builtin-seek) builtin for random-access file operations.

      Example:
        ```exec 3<> data.bin```
        ```seek 3 0 set           # seek to beginning```

==============================================================================
4. File Descriptor Duplication                 *redir-dup*

  `command N>&M`                               *redir-dup-out*

      Duplicate output file descriptor {M} onto {N}. After this, writing
      to fd {N} goes to the same place as fd {M}.

      Example:
        ```command > out.txt 2>&1  # stderr goes where stdout goes```

  `command N<&M`                               *redir-dup-in*

      Duplicate input file descriptor {M} onto {N}.

  `command N>&word`                            *redir-dup-word*
  `command N<&word`

      The source {M} need not be a literal number. It is a word subject
      to the usual expansions, and what it expands to selects the action:

          a run of digits   duplicate that descriptor
          `-`               close descriptor {N}
          anything else     an "ambiguous redirect" error: the command is
                            not run and the exit status is non-zero

      This lets the source descriptor be dynamic. It pairs naturally with
      descriptors allocated at runtime, such as the one |sock|(builtin-sock)
      stores in `$SHED_CONN`:

        ```fd=1; echo hi >&$fd       # write to the fd named by $fd```
        ```read line <&"$conn"       # quotes work too```
        ```cat <&$((base + 1))       # as does arithmetic```

  `command N>&-`                               *redir-close-out*
  `command N<&-`                               *redir-close-in*

      Close file descriptor {N}. Because the source is expanded, a word
      that evaluates to `-` closes the descriptor as well: with ```d=-```,
      ```exec 3>&$d``` is equivalent to ```exec 3>&-```.

      Example:
        ```exec 3>&-              # close fd 3```

==============================================================================
5. Pipelines                                   *redir-pipe*

  `command1 | command2`                        *pipe*

      Connect stdout of {command1} to stdin of {command2}. External stages
      run concurrently as separate processes.

      Example:
        ```cat file.txt | grep pattern | sort```

      Two |shopt|s control how stages run. `core.pipeline_style` selects
      the execution mechanism:

        `fork`    every stage runs in its own forked subshell (matches
                  `bash`)
        `thread`  builtin stages run as in-process threads instead of
                  forking; external stages still fork (the default)

      `core.lastpipe` selects whether the *final* stage runs in the
      current shell, so its side effects, variable assignments, `read`,
      `cd`, persist after the pipeline ends:

        `true`    the last stage runs in the current shell when it is a
                  builtin or function (the default, like `bash`'s
                  `shopt -s lastpipe`)
        `false`   the last stage is isolated like every other stage,
                  matching `bash`'s default

      With the default `core.lastpipe=true`:

        ```printf '%s\n' a b c | while read x; do n=$((n + 1)); done```
        ```echo "$n"        # prints 3```

      Only the final stage can run in the current shell; an earlier
      builtin (```read x | cat```) is always isolated and loses its
      assignments, whatever the style. See |shed-extensions|.

  `command1 |& command2`                       *pipe-and*

      Connect both stdout and stderr of {command1} to stdin of {command2}.
      Equivalent to `command1 2>&1 | command2`.

==============================================================================
6. Here Documents                              *heredoc*

  `command << DELIM`                           *redir-heredoc*

      Read input from the script body until a line containing only {DELIM}
      is found. The text between is fed to stdin of {command}.

      Parameter expansion, command substitution, and arithmetic expansion
      are performed in the body unless the delimiter is quoted.

      Example:
        ```cat << EOF
        Hello $USER
        EOF```

  `command << 'DELIM'`                         *redir-heredoc-literal*

      Quoting the delimiter (single or double quotes) suppresses all
      expansion in the heredoc body. The text is passed literally.

      Example:
        ```cat << 'EOF'
        This $variable is not expanded
        EOF```

  `command <<- DELIM`                          *redir-heredoc-indent*

      Like `<<` but strips leading tab characters from each line of the
      body and from the closing delimiter. This allows heredocs to be
      indented for readability without affecting the content.

      Example:
        ```if true; then
         cat <<- EOF
         indented content
         EOF
        fi```

==============================================================================
7. Here Strings                                *herestring*

  `command <<< word`                           *redir-herestring*

      Feed {word} as a single string to stdin of {command}, with a
      trailing newline appended. {word} is subject to the usual expansions.

      Example:
        ```read first rest <<< "hello world"```
        ```bc <<< "2 + 2"```

==============================================================================
8. File Descriptor Numbers                     *redir-fd*

  Any redirection operator can be prefixed with a file descriptor number:

      `2> file`       redirect stderr to file
      `3< file`       open file on fd 3
      `4>> file`      append to file on fd 4
      `5<> file`      open file read-write on fd 5

  Standard file descriptors:

      0   stdin
      1   stdout
      2   stderr

  Descriptors 3 through 9 are yours to use. Ten and above are reserved:
  the shell allocates from there for |redir-varfd|, and a written number
  in that range is refused, so a script can never collide with one.

==============================================================================
9. Allocated Descriptors                       *redir-varfd*

  `{name}` in place of a descriptor number lets the shell pick one and
  tells you which, rather than making you choose a number and hope
  nothing else wants it.

      ```exec {fd}< data.txt```
      ```thru <&$fd```
      ```exec {fd}<&-```

  The descriptor it picked is assigned to {name} as an ordinary variable,
  so everything afterwards refers to it as `$name`. Allocation takes the
  lowest free descriptor at 10 or above -- outside the range a script
  writes by hand, which is what makes a collision impossible.

  Every operator that opens a descriptor allocates one:

      `{v}< file`     `{v}> file`     `{v}>> file`    `{v}<> file`
      `{v}>&1`        `{v}<&0`

  Closing does not, because the descriptor already exists: `{v}>&-` reads
  {name} and closes what it names.

  Lifetime ~                                   *redir-varfd-lifetime*

    An allocated descriptor lasts as long as the redirection that made
    it, exactly like a numbered one. On `exec` that is the rest of the
    shell; on any other command it is that command only:

        ```exec {fd}< data.txt```     open until you close it
        ```true {fd}< data.txt```     closed when `true` returns

    The variable is not unset when the descriptor goes away, so after the
    second line `$fd` still holds a number that no longer names anything.
    Reading from it fails with `Bad file descriptor`.

    This differs from `bash`, which leaves the descriptor open after the
    command and relies on you to close it.

  Examples ~

      ```exec {lock}> /var/lock/mine```
      ```flock -n $lock || return```

      ```exec {log}>> run.log```
      ```echo starting >&$log```
      ```exec {log}>&-```

    A compound command keeps the descriptor for its whole body, which is
    where a non-`exec` allocation is useful:

      ```{ echo a >&$w; echo b >&$w; } {w}> out.txt```

==============================================================================
10. Variable Redirection                       *redir-var*

  Redirect a command's output into a shell variable, or feed a variable's
  contents in as its input. Unlike command substitution, which strips newlines,
  the capture is byte-exact.

  `command >@name`                             *redir-out-var*

      Capture the command's stdout into `$name`, replacing any previous
      value.

      Example:
        ```ls -d / >@root```
        ```printf '%s' "$root"    # / and the newline ls printed```

  `command >>@name`                            *redir-append-var*

      Append the command's stdout to `$name`, keeping its existing value.

      Example:
        ```log=start```
        ```echo ' more' >>@log```

  `command <@name`                             *redir-in-var*

      Feed the contents of `$name` to the command's stdin. `$name` is not
      modified.

      Example:
        ```text=hello```
        ```cat <@text```

  A descriptor number applies as it does to file redirections, so
  `command 2>@errs` captures stderr, and both streams can be captured
  separately in one run:

      ```command >@out 2>@err```   captures both the stdout and stderr
                                   of `command` into separate variables

  Byte transparency ~

    Command substitution strips trailing newlines, and in other POSIX
    shells a variable cannot hold a NUL byte at all. A variable
    redirection preserves both, so arbitrary bytes round-trip:

      ```cat image.png >@blob```
      ```printf '%s' "$blob" > copy.png    # identical to the original```

    Measure a capture with |len -b|(builtin-len). The POSIX `${#var}`
    form counts characters, which differs from the byte count for
    non-ASCII input.

  Subscripts ~

    The target may name an array element. The subscript is expanded the
    same way |redir-varfd| expands its braces, so a variable or an
    arithmetic expression works:

      ```printf a >@arr[0]```
      ```printf b >@arr[$i]```
      ```printf c >@arr[1+1]```

    An indexed array is created if the variable is unset. An associative
    array must be declared first with |declare|(builtin-declare) and
    `-A`; otherwise the subscript is treated as arithmetic instead of a key,
    and evaluates to index 0.

  Scope ~

    A capture reaches the shell that ran the pipeline, whichever stage made
    it. This differs from an ordinary assignment, which does not survive a
    stage:

      ```printf x | cat >@out | cat    # $out is set afterwards```
      ```printf x | read v | cat       # $v is not```

    With `exec`, the descriptor outlives the command and the capture is
    committed when it closes:

      ```exec 7>@out```
      ```echo captured >&7```
      ```exec 7>&-              # $out is set now```

  Limits ~

    A capture is bounded by the `core.max_read_limit` |shopt|. Output
    past the limit is discarded and a warning is printed; the command's
    exit status is not changed.

  The variable name ends at the first character that cannot appear in a
  name, so `>@a-b` captures into `a` and passes `-b` to the command as
  an argument.

  A capture made inside the body of a compound command or function cannot
  travel back out if that body runs in a forked process. A body forks when
  it contains an external command, and `(` `)` always forks:

      ```printf x | { thru >@a; } | thru       # $a is set```
      ```printf x | { cat >@b; } | cat         # $b is not```
      ```printf x | ( thru >@c ) | thru        # $c is not```

  The redirection itself is unaffected -- the command still writes where it
  was told to. Only the commit is lost, the same way any other variable
  write inside a subshell is lost. Capture at the stage itself rather than
  inside its body to avoid this:

      ```printf x | cat >@b | cat              # $b is set```

==============================================================================
11. Combining Redirections                     *redir-combine*

  Multiple redirections can appear on a single command, processed left
  to right:

      ```command > out.txt 2>&1   # stdout to file, stderr to same file```
      ```command 2>&1 > out.txt   # different! stderr to terminal,
                                 # stdout to file```

  Order matters: each redirection is applied in sequence. When using the dup
  form like `2>&1`, `2` now points where `1` is pointing. Redirecting `1` at
  this point will change where `1` is pointing, but `2` does {not} inherit this
  change. It will continue pointing where `1` used to.
